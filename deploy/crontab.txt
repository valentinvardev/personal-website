# Cron del panel de medición, para el VPS.
#
# Instalar con:  crontab -e   (y pegar la línea de abajo)
# Verificar con: crontab -l
#
# ---------------------------------------------------------------------------
# Por qué la hora está en UTC y no se usa CRON_TZ
# ---------------------------------------------------------------------------
# El día lógico corta a las 5:00 de Buenos Aires, así que el rollup tiene que
# correr DESPUÉS de esa hora: a medianoche estaría consolidando un día todavía
# abierto y nadie se enteraría, porque el resultado sería plausible.
#
# 08:30 UTC = 05:30 America/Argentina/Buenos_Aires (UTC-3), media hora después
# del corte. NO se usa CRON_TZ: si el daemon lo ignora (varía según la
# distribución), el job correría tres horas antes y el error sería invisible.
# Buenos Aires no tiene horario de verano desde 2010, así que el offset es fijo.
#
# ---------------------------------------------------------------------------
# Por qué cada pedazo de la línea está ahí
# ---------------------------------------------------------------------------
#   cd ...            el CLI resuelve rutas relativas al repo
#   mkdir -p logs     `logs/` está en .gitignore, así que en un clone limpio no
#                     existe y la redirección fallaría ANTES de ejecutar nada:
#                     el síntoma sería "no hay datos" sin un solo error visible
#   flock -n          si una corrida anterior quedó colgada, la siguiente no se
#                     superpone contra la misma base
#   --env-file=.env   el CLI necesita DIRECT_URL
#   --catchup         recupera los días que falten si el VPS estuvo caído, y
#                     recomputa los últimos 2 por si hubo carga retrospectiva
#   >> ... 2>&1       todo al log, incluido el stderr
#
# ---------------------------------------------------------------------------
# La ruta al binario de Node va COMPLETA en cada línea, y no en un PATH global
# ---------------------------------------------------------------------------
# Dos razones, las dos aprendidas rompiéndolo.
#
# 1. Los CLI del panel son TypeScript y se ejecutan con `node` directo, apoyados
#    en el type-stripping nativo, que existe recién desde Node 22.6. El Node del
#    sistema en el VPS es el 20 (paquete de NodeSource), y ahí mueren con
#    ERR_UNKNOWN_FILE_EXTENSION ".ts". Peor: mueren ANTES de crear la fila en
#    JobRun, así que la bitácora que existe justo para detectar "el cron dejó de
#    andar" no ve nada. Por eso el panel además cuenta días sin consolidar
#    (freshness.pendingDays), que es la única señal que sobrevive a esto.
#
#    La solución NO es cambiar el Node del sistema: ese VPS corre once apps bajo
#    el mismo pm2 y ninguna es nuestra para romper. Node 22 vive aparte, dentro
#    del home, y solo lo usan estas tres líneas.
#
# 2. Un `PATH=...` arriba del crontab aplica a TODAS las entradas del archivo,
#    incluidas las de las otras apps del mismo usuario. Poner Node 22 primero
#    ahí les cambiaría el intérprete a espaldas de quien las escribió. Una ruta
#    absoluta por línea toca exactamente lo que tiene que tocar.
#
# Si moviste Node a otro lado, cambiá NODE22 en las tres líneas. Verificá con:
#   /home/photoplatform/node22/bin/node -v     # tiene que decir v22.x
SHELL=/bin/bash

# Rollup diario.
30 8 * * * cd /home/photoplatform/valentinvarela && mkdir -p logs && /usr/bin/flock -n /tmp/vv-panel-rollup.lock /home/photoplatform/node22/bin/node --env-file=.env scripts/panel-job.ts rollup --catchup >> logs/panel.log 2>&1

# Reprocesa entregas de webhook que quedaron colgadas. GitHub no reintenta las
# entregas fallidas de un webhook de repositorio, así que sin esto un fallo del
# procesamiento en background hace desaparecer commits para siempre.
40 8 * * * cd /home/photoplatform/valentinvarela && mkdir -p logs && /usr/bin/flock -n /tmp/vv-panel-inbox.lock /home/photoplatform/node22/bin/node --env-file=.env scripts/panel-job.ts inbox >> logs/panel.log 2>&1

# Backup semanal, los domingos. El README y panel-export.ts sostienen que el
# backup de verdad es el CLI: acá es donde eso se vuelve cierto.
0 9 * * 0 cd /home/photoplatform/valentinvarela && mkdir -p logs && /home/photoplatform/node22/bin/node --env-file=.env scripts/panel-export.ts >> logs/panel.log 2>&1 && find backups -name 'panel-*.json' -mtime +60 -delete

# "weekly, rotate 8, compress, missingok, notifempty" alcanza.
